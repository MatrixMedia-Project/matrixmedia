# Secrets inventory (compose path)

Every secret the installer generates into `$MM_ROOT/.env.secrets`
(`deploy/lib/secrets.sh: generate_secrets`), traced through
`deploy/docker-compose.tmpl.yml` (DC) and `deploy/templates/*`.
Rotation procedures live in [rotation-runbooks.md](rotation-runbooks.md) and
are executed by `mmctl rotate <SECRET_NAME>`.

How secrets are born:

- `gen_secret KEY [HEXLEN]` appends `KEY=<openssl rand -hex>` **only if
  absent** — generate-once by contract, never rotates. `gen_literal` does the
  same for fixed values. Rotation goes through `_upsert_secret` instead.
- `write_secret_files` materialises exactly 4 Docker secret files under
  `$MM_ROOT/secrets/` (`mm_db_app_password`, `mm_db_admin_password`,
  `synapse_registration_shared_secret`, `signup_ip_hash_pepper`), written with
  `printf '%s'` so no trailing newline reaches the consuming process.
- `render_templates` bakes values into rendered configs under
  `$MM_ROOT/config/`; the compose file itself is interpolated at up-time from
  both env files.
- `capture_admin_token` (bootstrap) overwrites the placeholder
  `MM_SYNAPSE_ADMIN_TOKEN` with a real Synapse access token for the owner.

## Inventory

| Secret | Generated by | Consumed by | Blast radius if leaked |
|---|---|---|---|
| `LK_API_KEY` | `gen_literal` (fixed) | LiveKit `keys:` + webhook; egress/ingress configs; mm-core; lk-jwt-service | None alone — pairs with `LK_API_SECRET` |
| `LK_API_SECRET` | `gen_secret 64` | Same five consumers as `LK_API_KEY` | **High** — forge LiveKit access tokens; impersonate the SFU webhook |
| `MM_AS_TOKEN` | `gen_secret 64` | mm-core env; Synapse appservice registration (`mm_appservice.yaml`) | **Critical** — full appservice authority against Synapse |
| `MM_HS_TOKEN` | `gen_secret 64` | mm-core env; appservice registration | **High** — spoof Synapse→mm-core appservice transactions |
| `MM_ADMIN_TOKEN` | `gen_secret 64` | mm-core env; compose healthcheck header; `mmctl doctor` | **Critical** — mm-core admin API (`/_mm/admin` is internet-routed) |
| `MM_JWT_SIGNING_KEY` | `gen_secret 64` | mm-core env only — signs session/refresh/admin JWTs | **Critical** — forge any user or admin session token |
| `MM_SWITCH_AUTH_SECRET` | `gen_secret 64` | mm-core (signs HMAC tokens); mm-switch (verifies) | **High** — mint switch control tokens; hijack/record/relay streams |
| `MM_SIGNUP_IP_HASH_PEPPER` | `gen_secret 64` | Docker secret file → mm-core | **Low** — offline brute-force of signup rate-limit hashes |
| `MM_SETTINGS_ENCRYPTION_KEY` | `gen_secret 64` | mm-core env only — encrypts secret settings saved from the dashboard | **High** — together with a database dump, decrypts the stored Stripe/S3/LNbits secrets |
| `SYNAPSE_REGISTRATION_SECRET` | `gen_secret 64` | `homeserver.yaml`; Docker secret file → mm-core; installer registration | **Critical** — register arbitrary users including admins |
| `SYNAPSE_MACAROON_SECRET` | `gen_secret 64` | `homeserver.yaml` | **High** — forge Synapse-issued macaroons |
| `SYNAPSE_FORM_SECRET` | `gen_secret 64` | `homeserver.yaml` | **Low** — forge Synapse HTML-flow form tokens |
| `POSTGRES_SYNAPSE_PASS` | `gen_secret 32` | postgres env (**initdb-only**); `homeserver.yaml` | **Critical** — full Synapse DB (internal network only) |
| `POSTGRES_APP_ADMIN_PASS` | `gen_secret 32` | secret file → mm-postgres (initdb-only); `mm_admin` role; mm-core DB URLs | **Critical** — full MatrixMedia app DB (mm-db-net only) |
| `POSTGRES_APP_PASS` | `gen_secret 32` | `mm_app` role in init SQL; secret file. **No live consumer** — mm-core connects as `mm_admin` | **High** — read/write app tables |
| `REDIS_PASSWORD` | `gen_secret 32` | lk-redis `--requirepass` + healthcheck; LiveKit config | **Low/Medium** — LiveKit room-state tampering (internal only) |
| `TURN_USER` / `TURN_PASS` | `gen_literal` / `gen_secret 32` | coturn long-term credential; mm-switch env | **Medium** — free relay bandwidth |
| `MM_SYNAPSE_ADMIN_TOKEN` | placeholder, overwritten by `capture_admin_token` | mm-core env; `mmctl doctor` | **Critical** — Synapse admin API as the server owner |
| `MM_OWNER_BOOTSTRAP_PASS` | `install.sh` (only when no `--admin-pass` is given); persisted via `_upsert_secret` | `install.sh` itself on re-runs — reused to converge `register_new_matrix_user`/`capture_admin_token` against the same owner account instead of dying on "admin exists with a different password" | **Critical** — the server owner's Matrix account password |

> **`MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`** are no longer generated. MinIO was
> removed from the stack on 2026-09-26 (nothing used it, and its images stopped being
> publicly pullable). Installs created before then still have both keys in `.env`;
> they are inert and can be deleted. The old container is removed by the next
> `mmctl update` (`--remove-orphans`); its `minio-data` volume is not, and holds only
> MinIO's own metadata — remove it with `docker volume rm <project>_minio-data`.

Operator-supplied secrets live in `$MM_ROOT/.env` (written by `install.sh`,
not generated): `MM_STRIPE_SECRET_KEY`, `MM_STRIPE_WEBHOOK_SECRET`,
`MM_LNBITS_INVOICE_KEY`, `MM_LNBITS_ADMIN_KEY`. Rotate them at the provider,
paste the new value into `$MM_ROOT/.env`, then
`docker compose ... up -d --force-recreate mm-core`.

`MM_OWNER_BOOTSTRAP_PASS` is not a Docker secret — it lives in
`$MM_ROOT/.env.secrets` alongside the generated secrets above, but unlike
them it is only ever written when the operator didn't supply `--admin-pass`.
Rotate it by changing the owner account's password in the app (or via
Synapse admin API) and then either updating the value in `.env.secrets` to
match or removing the key entirely — a missing key just means the next
`install.sh` re-run generates and persists a fresh one.
